# DruMaster スマホ軽量化 結果レポート

作成日: 2026-09-01  
対象: DruMaster スマホ演奏画面  
主目的: 通常演奏 / どこでもタッチ / AUTO / 楽譜再生で、演奏時間・打鍵数の増加に伴って発生していた「ブツブツ途切れる」「終盤ほど悪化する」症状の軽減

## 1. 結論

今回のテストでは、最も悪化していた状態から、Audio Voiceプール導入後のPass 8でほぼ60fpsへ回復した。

主要な実測改善は以下。

- ブラウザ描画更新: **32.7 Hz → 59.7 Hz**（+82.6%）
- DruMaster実描画: **37.6 fps → 59.7 fps**（+58.8%）
- 直近5秒平均実描画: **37.4 fps → 59.7 fps**（+59.6%）
- 50ms超停止の発生率: **33.7回/分 → 3.21回/分**（-90.5%）
- 最大描画停止: **444.4 ms → 117.7 ms**（-73.5%）
- 60Hz基準のdisplay不足分: **27.3 Hz不足 → 0.3 Hz不足**（不足量-98.9%）

さらにPass 9では入力UI処理を削減し、Pass 8比で:

- input平均処理時間: **4.576 ms → 0.278 ms**（-93.9%）
- input最大処理時間: **26.9 ms → 14.7 ms**（-45.4%）

最終的に本番へ反映したのは、効果が明確だった **Pass 8 Audio Voiceプール** と **Pass 9 判定UIキャッシュ**。本番でもユーザー実機で最後まで問題なく演奏でき、体感上もかなり軽くなったことを確認した。

---

## 2. 測定上の注意

以下の数値は同一スマホ環境で取得した診断オーバーレイのスクリーンショットを基にしているが、厳密なラボベンチマークではない。

特に各Passで:

- 曲中位置
- 打鍵数
- 診断オーバーレイの内容
- その瞬間のブラウザ/OS状態

が完全には一致しない。

そのため、FPSなどは実測値として有用だが、Pass間の差を100%純粋なA/B差とみなさないこと。

一方、**Pass 7 → Pass 8は既存の描画最適化をほぼ同じ状態で維持したままAudio Voice管理方式を変えた比較**なので、Audio Voiceプールの効果を見る比較として特に重要。

- Before: 32.7 Hz
- Pass 8: 59.7 Hz

- 32.7Hz: 約30.6ms/フレーム
- 59.7Hz: 約16.8ms/フレーム

ほぼ60Hz本来の更新間隔へ戻った。

### 4.2 DruMaster実描画FPS

- Before: 37.6 fps
- Pass 8: 59.7 fps
- 改善: **+22.1 fps / +58.8%**

直近5秒平均:

- Before: 37.4 fps
- Pass 8: 59.7 fps
- 改善: **+59.6%**

### 4.3 50ms超の停止

Passごとの経過時間が異なるため、1分あたりへ正規化。

- 117.7ms ≒ 約7.1フレーム分停止

## 5. Pass 7 → Pass 8: Audio Voiceプールの効果

Pass 8で入れた重要変更:

- AudioBufferSourceNodeはWeb Audio仕様どおり1打ごとに新規生成
- GainNodeは毎打鍵生成せず、Voiceスロットとして再利用
- Voice管理オブジェクトも再利用
- source終了時にGainNodeを破棄せずプールへ戻す
- シンバル等の余韻は維持
- Voice上限/Voice stealingは導入しない

Pass 7の比較用測定からPass 8終盤まで:

| 指標 | Pass 7 | Pass 8 | 改善 |
|---|---:|---:|---:|
| display | 39.5 Hz | 59.7 Hz | **+51.1%** |
| chart | 45.8 fps | 59.7 fps | **+30.3%** |
| chart 5秒平均 | 40.1 fps | 59.7 fps | **+48.9%** |
| >50ms/分 | 18.5 | 3.21 | **-82.6%** |
| 最大停止 | 171.7 ms | 117.7 ms | **-31.5%** |

これは今回の最重要結果。

### Audio Voice管理の健全性

Pass 8終盤:

- active voices: 0
- peak voices: 37
- gainPool: 37
- sources created: 2082
- ended: 2082

`peak voices == gainPool` となり、GainNodeプールが必要最大同時発音数で頭打ちになった。

また `sources == ended` なので、測定時点で生成したSourceが全て正常終了しており、Sourceが打鍵数に比例して残留している形跡はない。

Pass 9途中でも:

- voices: 16
- peak: 22
- gainPool: 22
- sources: 1764
- ended: 1748

ここで `1764 - 1748 = 16` で、差分がその瞬間のactive voices 16と一致する。

つまり、**終了済みSourceが溜まり続けるリークではなく、現在鳴っているVoiceだけが残る正常な状態**になっている。

## 6. Pass 8 → Pass 9: 入力UI処理の軽量化

Pass 9で削減したもの:

- 打鍵ごとの `canvas.clientWidth / clientHeight` 再取得
- 打鍵ごとの `measureText("PERFECT")`
- 判定文字位置の毎回style再設定
- 同一レーン/音種の発光style再書き込み
- 同一判定文字/gradeのDOM再書き込み

結果:

| 指標 | Pass 8 | Pass 9 | 改善 |
|---|---:|---:|---:|
| input平均 | 4.576 ms | 0.278 ms | **-93.9%** |
| input最大 | 26.9 ms | 14.7 ms | **-45.4%** |

Pass 9診断値:

- `judge geom 2`
- `measure 1`
- `judge style 216`
- `skip 1256`

1223タップまで進んでもgeometry再計算2回、文字幅計測1回で済んでおり、打鍵数に比例したレイアウト計算をほぼ排除できた。

---

## 7. Audio処理そのもののコスト

Pass 8終盤:

- playDrum平均: **0.232 ms**
- playDrum最大: **1.6 ms**

Voiceプール導入後は、音を鳴らす同期処理自体は1打あたりサブミリ秒級に収まっている。

したがって、改善後のAudio経路は60fpsの1フレーム予算16.7msに対して十分小さい。

---

## 8. 今回の原因として最も有力なもの

症状は当初:

- 演奏開始直後は正常
- 20〜30秒付近からブツブツし始める
- 打鍵回数が増えるほど悪化
- 終盤ではdisplay自体が30〜40Hz台まで落ちる

だった。

描画・Canvas・rAF・アニメーション生成を先に削減しても、打鍵数に応じた悪化は残った。

Pass 8でWeb Audio経路を:

`毎打鍵: Source + Gain新規生成`  
から  
`毎打鍵: Sourceのみ新規 / GainはVoiceプール再利用`

へ変更すると、終盤1367タップ時点でも59.7fpsを維持した。

このため、今回の主要症状については、**打鍵ごとのGainNode生成・接続・破棄を含むWeb Audioグラフ churn が主要因だった可能性が非常に高い**。

Pass 9ではさらに入力UIの同期処理を削減し、単発フレーム落ちの要因を減らした。

本番反映前バックアップ:

`backup/drumaster-pre-mobile-perf-20260901`

本番反映後、ユーザー実機で最後まで問題なく演奏でき、体感上も「かなり軽くなった」と確認。

## 10. 「本番FPS」についての注意

59.7fpsという数値は累積テスト環境Pass 8での実測値。

最終本番は安全性を優先してPass 8/9の主要部分だけを反映したため、**本番そのもののFPSを診断オーバーレイで再測定した値ではない**。

したがって正確な表現は:

- テスト環境では、最悪32.7Hz / 37.6fps級から59.7Hz / 59.7fpsまで改善を実測
- 本番には主要因だったPass 8/9を反映
- 本番実機では完奏と体感改善を確認

となる。

将来さらに厳密な本番ベンチマークを取る場合は、本番へコード変更を入れずに使える一時診断入口を用意し、同一曲・同一モード・同一打鍵パターンでBefore/After測定する。

## 11. 今後の基準値

今回の安定状態を今後の性能回帰チェック基準とする。

目標:

- display: **58〜60Hz前後**
- chart: **58〜60fps前後**
- 演奏終盤まで継続的なFPS低下がない
- 打鍵数増加に伴うフレームレート劣化がない
- Gain poolはpeak voice付近で頭打ち
- `sources - ended ≒ active voices`
- playDrum同期CPUは概ね1ms未満、突発でも数ms以内
- input同期CPUは平均1ms未満を目標

今回のPass 8/9結果は、この基準を概ね満たした。
