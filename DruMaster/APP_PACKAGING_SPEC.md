# DruMaster アプリ化仕様書

- **Status:** Active / Normative
- **Version:** 1.0
- **Last Updated:** 2026-08-30
- **Scope:** DruMaster Web / Android / Desktop / future iOS

この文書は、DruMaster を Web アプリとして維持しながら Android・PC 等へパッケージ化していく際の実装判断基準とする。
アプリ化に関する設計変更を行う場合は、実装と同時に本仕様書も更新する。

## 1. 基本方針

1. 現在の Web 版 DruMaster を **基準実装（single source of truth）** とする。
2. GitHub Pages 版の動作を維持したまま、同じ HTML / CSS / JavaScript / 楽曲データ / 画像 / 音源を可能な限り各プラットフォームで共有する。
3. Android / Windows / iOS のためだけにゲーム本体を全面的に書き直さない。
4. プラットフォーム固有処理が必要になった場合は、ゲーム本体から分離した adapter / plugin / interface 層として追加する。
5. パッケージ化を理由に、既存の判定ロジック、譜面仕様、音量バランス、再生タイミング、UI レイアウト等を不用意に変更しない。

## 2. 内部 URL・パスの規則

### 2.1 必須規則

- DruMaster 自身が保持する HTML / CSS / JavaScript / JSON / MIDI / 音源 / 画像 / フォント等は、原則として **相対パス** で参照する。
- 自サイトの本番 Origin をハードコードしない。
  - 禁止例: `https://ld1kanae.github.io/DruMaster/...`
- `localhost`、固定開発サーバー URL、`file://` への依存を本番コードへ持ち込まない。
- アプリ内資産については、可能な限り `/DruMaster/...` のような Origin ルート基準の絶対パスも避ける。
- GitHub Pages 上でもパッケージ版でも同じ相対参照が成立する構成を優先する。

### 2.2 絶対 URL を維持してよいもの

以下は DruMaster 内部資産ではないため、必要なら絶対 URL を使用してよい。

- GitHub REST API 等の外部 API endpoint
- GitHub の Personal Access Token 作成・管理ページ
- 外部 CDN
- 外部ドキュメント、外部サービスへのリンク
- その他、別 Origin に存在すること自体が仕様であるリソース

外部 URL を機械的に相対化してはならない。

## 3. Web 版

- GitHub Pages 版は継続して正式サポートする。
- アプリ化後も Web 版を廃止しない。
- Web 版とパッケージ版で譜面・楽曲定義・判定・基本 UI のコードを分岐させないことを優先する。
- パッケージ対応変更後は、GitHub Pages からの通常起動・リロード・楽曲切替が従来どおり動作することを確認する。

## 4. Android

### 4.1 第一候補

**Capacitor を第一候補とする。**

既存の Web 実装を WebView 内で動作させ、必要な箇所だけ Android ネイティブ機能へ接続する。

### 4.2 導入順序

1. 既存 Web 版をほぼ変更せず Capacitor コンテナで起動する。
2. APK / AAB を実機へインストールし、基本動作を検証する。
3. Android 固有機能を必要なものから追加する。
   - 横画面運用
   - immersive fullscreen
   - スリープ抑制
   - アプリ内ローカル資産
   - オフライン動作
   - 必要に応じたファイルアクセス
4. 入力・描画・音声を実機計測する。
5. WebView 実装で不足する部分だけ、ネイティブ実装を検討する。

### 4.3 配布

- 開発・実機検証段階では APK を利用できる。
- Google Play 配布を行う段階では署名・AAB・ストア要件を別途整備する。

## 5. Windows / PC

### 5.1 第一評価候補

**Tauri を第一評価候補とする。**

評価項目:

- アプリ容量
- メモリ・CPU 使用量
- Web Audio 互換性
- MIDI / 入力機器との互換性
- ファイルアクセス
- 開発・保守コスト

### 5.2 Electron を選択する条件

以下の場合は Electron を有力候補とする。

- Chromium を同梱することによる Web 実装との互換性が重要
- Web Audio / Web API の環境差を減らす必要がある
- Tauri で実機互換性上の問題が出る
- Node / Electron 向けエコシステムを利用する明確な利点がある

Tauri / Electron の選択は、推測ではなく DruMaster の実機検証結果で決定する。

## 6. iOS / iPadOS

- 将来対応時は Capacitor を第一候補とする。
- Android とゲーム本体を共有し、iOS 固有処理だけを platform adapter として分離する。
- iOS 対応を理由に Web / Android のゲームコアを複製しない。

## 7. 音声・入力・タイミング

### 7.1 重要原則

**パッケージ化しただけで入力遅延・音声遅延・音切れが解消するとはみなさない。**

Capacitor 版でも WebView 上の JavaScript / Web Audio / Canvas が基本となるため、まず現状のゲームループとオーディオ処理を計測する。

### 7.2 ネイティブ化の判断

以下の条件を満たした場合に限り、部分的なネイティブ化を検討する。

- 実機計測で WebView 固有の遅延または安定性問題が確認できる
- JavaScript 側の最適化では十分改善しない
- ネイティブ化による改善量を測定できる

候補:

- 低遅延ドラム音再生
- 高精度入力取得
- 必要に応じたオーディオデバイス制御

ネイティブ化する場合も、譜面時刻・判定時刻・再生時刻の基準を複数系統に分裂させない。

## 8. オフライン・アセット

- パッケージ版でゲーム進行に必須な内部アセットは、権利・容量上問題がない限りアプリ内へ同梱する。
- MIDI、譜面定義、UI 画像、ゲーム内ドラム音源等はネットワークなしでも読める構成を目標とする。
- 楽曲音源についても配布条件と容量を確認したうえで同梱可否を決める。
- アプリの基本起動や内部 UI は、外部サーバー障害によって起動不能にならない構成を優先する。

## 9. プラットフォーム固有コードの境界

ゲーム本体から直接 Android / Windows API を大量に呼ばない。

推奨構造の概念:

```text
DruMaster Web core
├─ UI / Canvas
├─ chart / judgement
├─ song / MIDI handling
├─ shared audio logic
└─ platform adapter
   ├─ Web
   ├─ Android (Capacitor / native plugin)
   ├─ Windows (Tauri or Electron)
   └─ iOS (future)
```

Web で完結できる処理は Web core に残す。

## 10. パッケージ関連変更の回帰確認

最低限、以下を確認する。

### Web / GitHub Pages

- 起動できる
- CSS / JS / 画像が欠落しない
- 楽曲一覧を読める
- MIDI / 譜面を読める
- 音源を読める
- START → 演奏 → 一時停止 → 再開 → 終了が動く
- 入力と判定が従来どおり動く
- リザルトが従来どおり動く
- 楽曲切替が動く
- 制作ツールの内部画面遷移が動く

### Android

- コールドスタートできる
- 横画面用レイアウトが崩れない
- fullscreen / immersive の挙動が仕様どおり
- 必須内部資産をロードできる
- オフライン対象の資産が通信なしで読める
- タッチ入力に欠落・大きな遅延がない
- 音声に顕著な途切れ・同期崩れがない
- バックグラウンド / 復帰時に不正状態にならない

### URL / path

- アプリ内資産の取得先に `https://ld1kanae.github.io/DruMaster/...` が残っていない
- 内部資産のために固定 Origin を要求していない
- 外部 API / 外部サイトの URL は誤って相対化されていない

## 11. 変更管理

- このファイルを DruMaster のアプリ化に関する **仕様書** として扱う。
- 本仕様書と実装が矛盾する場合、意図的な仕様変更でなければ本仕様書を優先して修正方針を決める。
- 方針変更が必要な場合は、理由を確認したうえで実装と本仕様書を同時に更新する。
- 一時的な検証コードを恒久仕様として扱わない。
- Web 版の既存動作を壊す可能性がある変更は、パッケージ化作業と無関係なリファクタリングと混在させない。
