# Hi-hat 音響学習と打点救済の検証（v68 / v69）

実施日: 2026-09-23（UTC）
状態: **研究モデルのみ保存。本番採譜は変更しない。**

## 目的と入力

Open/Closed の音色を学習し、実際の `drums.mp3` 採譜候補で改善するか検証した。ユーザー提供の完全同期 WAV/MIDI 5組について SHA-256 を `AI_HANDOFF_SYNC_HAT_V65.md` と照合し、全10ファイルの一致を確認した。5曲の `DruMaster/songs/<song>/drums.mp3` と、先行 v67 の**音声のみから作成済みの予測イベント**を採譜候補に用いた。今回の採譜候補は fresh Chromium で再生成したものではない。

教師・採点は MIDI から取得した。除外曲の MIDI を特徴計算、予測、閾値選択に入れない。予測時の入力は音声と生成済み候補のみ。時刻は `song.json` の `stemOffsetSec` と任意の `midiOffsetSec` を適用し、±80 ms の一対一で採点した。アルクアラウンド参照 Ride ±80 ms の HH 予測は、指示に従い HH 採点から除外した。この除外は評価時だけであり、曲名による runtime 分岐はない。

元GMD MIDIから得た既存の `models/gmd-hat-articulation-prior-v1.json` は**拍内位置に対する弱い特徴**として使用した。GMD/E-GMD の音声を今回新規ダウンロードして学習したわけではない。`arrangement/` の `results-arrangement-structure-v37.json` は offvocal の反復区間と同位置にある既存候補の割合として別実験に使用した。反復先の正解MIDIは使わない。

## v68: Open/Closed 既存候補の学習

4曲で学習し1曲を除外、これを5周。MP3 上の Hat/Open 候補は曲順で **272 / 430 / 585 / 1,007 / 1,286** 件。同期WAVからMIDI時刻で抽出した音響例は **494 / 795 / 1,161 / 1,367 / 1,757** 件。14個のアタック・高域減衰・次打直前tail・次打後choke特徴を用いた。MP3のみの実験では現行Open状態も一条件で加えた。同期WAVの教師例には予測Open状態が存在しないため、その条件では全データから当該特徴を外した。

| 比較条件 | 閾値・処理 | 5曲合算 HH macro F1 |
|---|---|---:|
| 現行候補 | 変更なし | **0.738864** |
| MP3音響だけのExtraTrees | 0.90、双方向 | 0.739041 |
| MP3音響＋現行判定のExtraTrees | 0.90、双方向 | 0.738864 |
| MP3音響＋arrangement反復のExtraTrees | 0.90、双方向 | 0.738864 |
| MP3＋同期WAV音響のExtraTrees | 0.90、双方向 | 0.735746 |
| MP3＋同期WAV音響＋GMD prior | 0.90、双方向 | 0.736506 |

0.60 / 0.75 / 0.90 の閾値、Open昇格のみ／双方向を**事前に列挙して全件報告**した。全結果と各曲の TP / Pred / Ref は `results-hat-mp3-transfer-v68.json` にある。MP3音響だけの最大差は +0.000178 と微小で、アルクアラウンドは **0.468501 → 0.465143** と悪化した。先に固定した「曲別退行なし」の採用条件を満たさない。閾値をこの5曲の正解でさらに最適化して本番採用することはしない。

この最大差の条件でもOpenは **TP 659/予測917/参照1,179 → TP 658/予測913/参照1,179** で、Open recallは実際には僅かに下がった。Closedは **TP 2,357/予測2,630/参照2,923 → TP 2,359/予測2,634/参照2,923**。合算F1の微差を大きな学習成果とは解釈しない。

100本のExtraTreesを5曲MP3候補から再学習した研究用モデルを `hat-mp3-transfer-v68-research-model.json` に保存した。**本番モデルではない**。このモデルは現行Open状態への依存が強く、その特徴のimportanceは0.568だった。状態を外すと判定は増えるが曲別退行が出る。Pythonで再計算したMP3特徴と保存済みChromium v63特徴のなないろ先頭3候補を比較した最大差は0.00034未満だった。

## v69: Open打点の候補検出

分類器を替えても救えない場所を測った。既存のHat/Ride候補から±80 msより遠い参照Openはアルクアラウンド64、ダイヤモンドヴァージン360、怪獣6、なないろ1、Ray34音。音声の5 kHz以上の正のスペクトルフラックスから、新しいピーク候補を作成した。現行金物の±80 ms内、二手が埋まった35 msクラスタは候補にしない。ピークから14音響特徴＋フラックス強度＋既存金物との距離を取り、曲単位除外でLogisticとExtraTreesを学習した。

新規ピークが参照Openの±80 msに到達できる数は、それぞれ **47/64、338/360、6/6、1/1、32/34**。したがって候補生成そのものには余地がある。ただし正誤分類がまだ弱く、後段を通した集計F1は改善しなかった。詳細は `results-hat-missing-onsets-v69.json`。ここでも参照MIDIは教師・採点だけであり、予測候補には渡していない。

具体的には、Logistic の閾値0.95では新規44音を足して **0.738864 → 0.738007**。ExtraTrees の閾値0.70以上では追加0音で完全一致、0.50では107音を足して **0.728132** まで下がった。

## 解釈と次の実装単位

現時点の主な障壁は **Open打点の候補漏れ**と、広く拾った候補の**誤追加抑制**。単にOpen/Closedの後段分類を強くしても、元の候補にないOpenは復元できない。今回の5曲は過去の実験にも使われているため、曲単位除外はこの学習周回のリークを防ぐが、未知曲の一般化保証にはならない。

1. 同期WAVでOpen発音位置・次打のchokeを教師にした高解像度候補生成器を作る。評価を「候補のOpen到達率」と「追加OpenのPrecision」に分離する。
2. 各音色の異なる録音を補うため、E-GMDの**音声付き**サブセットを採用する場合は、キット・演奏系列を同時に分けて評価する。GMDのMIDI先行priorだけを音色の教師と呼ばない。
3. `arrangement/` の反復は、offvocalが与えられ、かつ音響確率が曖昧な箇所だけの補助証拠とする。音響候補がない場所への無条件コピーはしない。
4. 新規候補→Open/Closed/Ride/Pedal分類→二手制約の順に統合し、完全に未使用の楽曲と5曲fresh Chromiumで採点する。Kick/Snare/Tom のイベント列一致、Closed非退行、最悪曲HH非退行を通ってから本番化する。

再現コマンド（リポジトリ直下、Python `numpy scipy scikit-learn mido` と `ffmpeg` が必要）:

```bash
python drumscribe/experiments/train_hat_mp3_transfer_v68.py
python drumscribe/experiments/train_hat_missing_onsets_v69.py
```

同期WAV/MIDIの本体はリポジトリに含めない。v68 スクリプトは実行時に、リポジトリの隣の `upload/` に4組、`project_sources/` に「なないろ」を置く想定である。元の入力SHA-256は `AI_HANDOFF_SYNC_HAT_V65.md` を参照。v69はリポジトリにある MP3 と chart.mid のみで再実行できる。
